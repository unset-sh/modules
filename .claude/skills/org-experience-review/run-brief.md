**Review run brief**

Copy and complete this brief for each run. Blank required fields block the affected work; reviewers should explain the missing prerequisite rather than guess.

| Field | Value to supply |
| --- | --- |
| Run name and date | [Required] |
| Target and version | [Required: interface, workflow, prototype or materials and build or capture identifier] |
| Evidence mode | [Interactive UI / screenshots / recording / specification; list artifacts] |
| Intended audience and context | [Known goals and relevant constraints; distinguish assumptions] |
| Intended experience | [For example: understand consequences, accomplish a useful goal, recover confidently] |
| Device and input | [Relevant display, input, browser or client, zoom and available accessibility settings] |
| Test environment and account | [Disposable test identity reference; no credentials in the brief] |
| Starting state | [Data/state required before each task] |
| Allowed actions | [Read-only unless specific test mutations are authorized] |
| Reset and isolation | [How state is restored; whether each session is independent] |
| Control task | [Simple tool/capability check that does not reveal the target journey] |
| Tasks and success conditions | [User goals and observable outcomes; no prescribed click paths] |
| Failure/recovery states | [Authorized fixtures or supplied captures; no production fault injection] |
| Scope exclusions | [Explicitly out of scope] |
| Models and tools | [Actual model/version/settings if exposed; tools and any unavailable capabilities] |
| Review budget | [Comparable time/action limits; reaching them means incomplete, not user abandonment] |
| Model calibration | [Optional matched smaller/stronger runs, or state calibration not performed] |
| Evidence location | [Where screenshots, recordings and reports may be saved] |
| Human follow-up | [Which intended feelings or assumptions must later be tested with people] |

Suggested task goals, to adapt to actual supported features:
1. Complete the first useful task using supplied fictional content.
2. Determine the consequences or audience of an action and inspect any available preview.
3. Correct an input mistake and revise a saved choice.
4. Where supported in the test fixture, inspect an interrupted or failed operation and recover.

Different perspectives review the same core journeys through their assigned questions. Add special input/display conditions only when relevant and record the difference. Compare models within the same perspective and conditions.
